## 3. Numbered discrepancy list

### Correctness bugs (behaviour ≠ documented guarantee)

**C1 — Retrain worker is a governance bypass path.** `ml/monitor/retrain_worker.py:121-127` selects every
`gold.retrain_requests` row with `status='pending'` and runs a training subprocess; it never checks that the
row's `action_id` has an `approved`/`auto_approved` audit row. Anyone/anything that can INSERT a row gets a
model trained. (Effect is candidate-only, and the live data shows no actual bypass — 0 unapproved requests —
but the invariant is enforced only by "nobody else writes the table".)

**C2 — `risk_tier: auto` is not an allow-list.** Docs (phase4 §2) and code comments promise an explicit,
reviewable allow-list restricted to reversible/informational actions. Code: `LoadRules` only validates the enum;
`AutoApproveAndExecute` only checks the *row's* tier, which the rule itself set. A rule
`{action: retrain_model, risk_tier: auto}` boots and executes with no human. `TestAutoTierIsAnExplicitAllowListPath`
proves the audit shape, not a list. Also `AutoApproveAndExecute` writes its `auto_approved` audit row *before*
`execute()` checks status, so calling it on an already-executed/rejected auto row leaves a misleading approval row.

**C3 — Duplicate pending proposals for one order (verified on real data).** H2 scoped the dedup key to
`prediction.id`, so any re-scoring of the same order (score-writer redelivery after restart — its `seen` set is
in memory — or the next replay loop, which re-emits the same order ids) proposes a *second* hold while the first is
still pending. Dev queue: **8 orders have 2 pending holds** (ids 38–45 vs 74–81; same entities). The key-format
change also had no migration. Effect-level impact is nil (idempotent upsert) but the reviewer queue is inflated.

**C4 — Reconciler fails *open* on a missing threshold.** `govern/reconcile.go:167` uses
`COALESCE((metrics->>'recommended_threshold')::float8, 0)`, so a model version with no threshold gets threshold
**0** and the rule `score >= registry.recommended_threshold` proposes a hold for every order. The comment at
`:160-163` and `:227-230` says the field is omitted "so the rule fails closed". Latent today (all fraud/bot
versions have a threshold; only old churn versions don't) but it is exactly the class of bug the last commit fixed.

**C5 — H4's boot check accepts fields no producer emits.** `playbook/schema.go` declares `anomaly.z_score`,
but neither the aggregator (`aggregator.go:301-311`) nor the score-writer (`service.go:393-404`) puts a z-score in the
payload. A rule on it boots cleanly and never fires — the precise silent failure H4 was written to prevent.
Also `registry.positive_rate` is emitted live (`service.go:353`) but not by the reconciler
(`reconcile.go:213-232`), so live and reconciled events differ. Nothing pins schema ↔ publishers (T5).

**C6 — Banner hysteresis leaks through the REST path.** `Surfaced` (`ratetrack.go:145`) only gates the SSE
frame (`service.go:410`). It is not persisted; `GET /api/v1/anomalies` returns all `status='open'` rows
(`store/realtime.go:56-59`) and `refreshOpenAnomalies()` (`app.js:299-309`, called at `:540`) shows the newest one
on every page load. First-window blips therefore reach the banner after a reload. 372 anomalies are open
(309 model, 63 statistical) — nothing ever resolves them (Phase 1 §10 defers the lifecycle), so the banner
effectively always shows something.

**C7 — Realtime retention/reconcile keyed on event time; replay emits simulated time.** Verified: replayed
`occurred_at` is 2016-09-04 → 2017-01-30 (loop `l0`), while `Retention` deletes
`gold.realtime_metrics WHERE bucket_start < now() - 3h` and `Reconcile` only looks at
`occurred_at >= now() - 3h`. I demonstrated on scratch that a 2017 bucket is purged and a 10-minute-old one kept.
Result: during replay the bucket table is wiped every 5-minute janitor tick, reconcile self-healing is inert, the
REST first-paint and the agent's `live_realtime` tool are empty when the producer is off — which is why eval q13
fails on dev right now. The integration test hides all of this by generating `time.Now()`-relative timestamps.

**C8 — (latent, code-reading only, not yet reproduced) simulated clock overtaking wall clock.** Each loop shifts
events ≈729 days forward. After ≈5 loops (~32 h at 2880×) replayed timestamps exceed `now`. `flushAndDetect`
only analyses buckets with `s.Before(now-1min)` (`aggregator.go:274`) and only evicts buckets older than
`now-10min` (`:423-428`), so future-dated buckets are never closed or evicted: detection stops, memory grows, and
the single bulk upsert (5 params/bucket, `:404-411`) eventually exceeds Postgres' 65,535-parameter cap, making
every flush fail. I will write the failing test first in Step 5 before treating this as confirmed.

**C9 — Silent train/serve skew is possible.** `ml/serve.py:83` does `features.get(c, 0.0)`, so any feature name
Go fails to send is scored as 0 with no error. Fraud names are pinned by a spec+tests; the 13 bot names are
hand-mirrored (`features.go:342-358` vs `train_bot.py:29-33`) with no test tying them, and no train/serve
value-parity test exists at all (T4).

**C10 — "Restart-safe" is only partly true.** (a) *Aggregator*: `n/mean/m2` are persisted, but the analysis
cursor `lastAnalyzed` (`aggregator.go:48,381`) is not, and franz-go autocommits (default, `kafka/client.go:30-39`)
so a crash redelivers up to the last commit window. At 2880× a 5 s window ≈ 4 simulated hours ≈ 240 minute
buckets, which are re-folded into the restored baseline (double-count). Save failures are logged at Debug only
(`:166`). (b) *Score-writer*: rings/rate windows snapshot every 30 s but offsets commit every ~5 s, so restored
state and stream position disagree in both directions; the `seen` claim-set is not snapshotted, so redelivered
orders get scored again (feeds C3); `RestoreState` dereferences `st.Rings` unconditionally in its log line
(`state.go:123-124`) after guarding it above.

**C11 — Drift "decay" doesn't measure decay, and thresholds differ from the docs.** Docs/catalog/README say
critical at 1.5×; code is warning 1.25× / critical 2.0× (`psi.py:74-75`; test pins 1.25/2.0). The "current WAPE"
is computed over the *trainer's own persisted held-out rows* (`metadata ? 'actual'`) across **all model versions**
(dev rows: `n=1072` = **4 model versions × 268** rows per forecast model) versus the registry WMAPE, so it can only ever return ≈1.0 — no live ground
truth ever arrives. `churn_decay` (schema.sql:66-68, psi.py docstring) is not implemented. This feeds
`retrain-on-critical-drift`.

**C12 — Grounding is weaker than "falsifiability beats recall".** Measured on the fake fixtures (6–8 observed
numbers): **~7 % of arbitrary integers in [1, 3000] are "grounded"** by R2 (pairwise sum/mean/|diff| across *any*
two values in a label, including different columns); direction is not checked (an answer saying revenue *fell* by 30
on a rising series is grounded); `PROSE_CONSTANTS` hard-codes 0.795 so a stale threshold grounds with **zero** tool
evidence. Real tool output has up to 50 rows, so R2's false-accept rate is higher than measured.
